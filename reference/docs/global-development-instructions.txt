# Global Development Instructions

本文件定义所有 Java / Spring Boot 项目默认遵守的个人开发与工程协作规范。

除非用户当前明确提出新的要求，否则必须遵守本文件。

规则优先级：

> 用户当前最新明确要求 > 当前项目/目录 AGENTS.md > 本文件 > 通用最佳实践

不得以“最佳实践”“更优雅”“更安全”“更现代”为理由，擅自修改已经确认的需求、架构、技术选型、业务规则和代码风格。

---

# 1. 核心原则

整体风格：

> **配置显式优先，代码简洁优先。**

具体理解：

```text
配置：显式、直接、少包装
代码：简洁、少样板、语义清晰
业务：真实、明确、不隐藏规则
架构：简单、扁平、不过度设计
协作：事实可追溯、决策可延续、实现可交接
```

遵循：

> 真实业务优先于技术形式。

> 可读性优先于代码行数。

> 简洁优先于机械样板代码。

> 当前需求优先于假想未来。

> 真实协议优先于经验猜测。

> 已确认设计未经要求不得修改。

> 样板代码可以隐藏，业务语义不能隐藏。

> 事实、决策、实现必须分离。

默认使用：

```text

单 Spring Boot Application
单部署单元
```

未经明确要求，不拆 Maven 多模块。

推荐：

```text

├── AGENTS.md
├── README.md
├── pom.xml
├── docs
├── reference
```

不要因为所谓“架构完整”默认拆成：

```text

```

原则：

> 一个工程能够清楚解决的问题，不拆成多个工程。

# 5. Service 规范

Service 接口统一放：

```text
service
```

Service 实现统一放：

```text

```

正确：

```text

├── UserService.java
└── impl
    └── UserServiceImpl.java
```

不要：

```text
service
├── UserService.java
└── UserServiceImpl.java
```

不要无意义增加：

```text
service.api
service.core
service.internal
```

# 7. Lombok 使用规范

允许并鼓励使用 Lombok 消除机械样板代码。

常用：

```java
@Data
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@RequiredArgsConstructor
@FieldDefaults
@Slf4j
```

普通 Bean 推荐：

```java
@Data
@FieldDefaults(level = AccessLevel.PRIVATE)
public class UserResponse {

    String id;
    String username;
    UserState state;

}
```

不需要手写大量 Getter / Setter。

原则：

> 能通过 Lombok 清晰减少样板代码时，优先使用 Lombok。

---

# 8. Spring Bean 注入规范

Spring Bean 优先使用：

```java
@RequiredArgsConstructor
@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)
```

推荐：

```java
@Service
@RequiredArgsConstructor
@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)
public class UserServiceImpl implements UserService {

    UserClient userClient;
    UserRepository userRepository;

}
```

不需要写：

```java
@Service
@RequiredArgsConstructor
public class UserServiceImpl implements UserService {

    private final UserClient userClient;
    private final UserRepository userRepository;

}
```

不要字段注入：

```java
@Autowired
private UserClient userClient;
```

原则：

> 构造器注入保留，`private final` 等机械样板交给 Lombok。

---

# 9. Builder 使用规范

默认不要滥用 `@Builder`。

简单对象优先：

```java
UserResponse response = new UserResponse();
response.setId(user.getId());
response.setUsername(user.getUsername());
response.setState(UserState.ENABLED);
```

不需要为了形式统一全部写成：

```java
UserResponse response = UserResponse.builder()
        .id(user.getId())
        .username(user.getUsername())
        .state(UserState.ENABLED)
        .build();
```

如果字段很多、构造复杂、Builder 确实提升阅读性，可以使用。

原则：

> Builder 是工具，不是默认对象创建方式。

---

# 10. 禁止使用 `var`

Java 局部变量必须使用显式类型。

禁止：

```java
var users = userService.list();
var response = new UserResponse();
var iterator = users.iterator();
```

使用：

```java
List<User> users = userService.list();
UserResponse response = new UserResponse();
Iterator<User> iterator = users.iterator();
```

即使当前 JDK 支持，也不要使用 `var`。

---

# 11. Lambda / Stream 规范

不要为了代码短而强行使用 Lambda / Stream。

简单、明确的转换可以使用。

复杂业务逻辑优先普通 `for`。

以下场景优先不用 Stream：

- 多个业务分支。
- 修改局部变量。
- 状态变化。
- 需要 `continue / break`。
- 复杂异常处理。
- 需要观察中间过程。
- Lambda 导致变量必须 final / effectively final。
- Stream 明显降低阅读性。

不推荐：

```java
List<UserResponse> responses = users.stream()
        .filter(user -> user.getState() == UserState.ENABLED)
        .map(user -> {
            UserResponse response = new UserResponse();
            response.setId(user.getId());
            response.setUsername(user.getUsername());
            return response;
        })
        .toList();
```

更推荐：

```java
List<UserResponse> responses = new ArrayList<>();

for (User user : users) {
    if (user.getState() != UserState.ENABLED) {
        continue;
    }

    UserResponse response = new UserResponse();
    response.setId(user.getId());
    response.setUsername(user.getUsername());

    responses.add(response);
}
```

原则：

> 少写几行不是目标，看一遍就懂才是目标。

# 12. 枚举规范

枚举元素一行一个。

中文含义统一写在枚举元素同行的行尾。

正确：

```java
public enum StoryState {

    PENDING_REVIEW, // 待评审
    PENDING_CLAIM,  // 待认领
    PROCESSING,     // 执行中
    COMPLETED       // 已完成

}
```

带参数：

```java
@Getter
@RequiredArgsConstructor
@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)
public enum SyncState {

    PENDING(0),    // 待同步
    PROCESSING(1), // 同步中
    SUCCESS(2),    // 成功
    FAILED(3);     // 失败

    int code;

}
```

不要：

```java
/**
 * 待评审。
 */
PENDING_REVIEW
```

也不要：

```java
PENDING_REVIEW, PENDING_CLAIM, PROCESSING, COMPLETED
```

---

# 13. `state` 与 `status`

本地业务对象表达当前状态时优先使用：

```text
state
```

例如：

```java
StoryState state;
```

而不是：

```java
StoryStatus status;
```

但远端协议必须尊重真实字段。

如果第三方返回：

```json
{
  "status": "DONE"
}
```

远端协议对象仍然保留：

```java
String status;
```

进入本地领域模型后，再根据需要转换：

```java
StoryState state;
```

原则：

> 本地命名可以统一，远端协议不能擅自改。

# 14. Controller 规范

Controller 必须保持薄。

Controller 只负责：

- 接收 HTTP 参数。
- 基础参数校验。
- 调用 Service。
- 返回统一响应。

Controller 不负责：

- 复杂业务判断。
- HTTP 远端调用。
- Cookie 管理。
- 数据库复杂组合。
- 同步逻辑。
- 重试逻辑。
- 状态机。
- 大量对象转换。

推荐：

```text
Controller
    ↓
Service
    ↓
Client / Mapper
```

示例：

```java
@RestController
@RequestMapping("/api/users")
@RequiredArgsConstructor
@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)
public class UserController {

    UserService userService;

    /**
     * 查询用户列表。
     * @return 用户列表
     */
    @GetMapping
    public ApiResponse<List<UserResponse>> list() {
        List<UserResponse> responses = userService.list();
        return ApiResponse.success(responses);
    }

}
```

---

# 15. Client 规范

第三方系统 HTTP 调用集中到 Client。

例如：

```text
WizardClient
MeetingClient
TokenClient
UserClient
```

Client 负责：

- HTTP 请求。
- Header。
- Cookie。
- 请求参数。
- 序列化。
- 反序列化。
- 远端错误识别。

Service 负责：

- 业务流程。
- Client 编排。
- 状态转换。
- 业务判断。

不要：

```text
Controller
    ↓
HttpClient
```

应当：

```text
Controller
    ↓
Service
    ↓
Client
    ↓
Remote System
```

---

# 16. 方法规范

方法应该职责明确。

不要写几百行超级方法。

但也不要机械拆成：

```text
execute()
    ↓
prepare()
    ↓
process()
    ↓
processInternal()
    ↓
doProcess()
    ↓
executeInternal()
```

以下情况才值得拆方法：

- 有明确独立业务语义。
- 重复逻辑需要复用。
- 能明显降低复杂度。
- 能提升阅读性。

不要仅仅为了减少单个方法行数而拆分。

---

# 17. 方法签名排版

合理长度的方法声明保持单行。

推荐：

```java
public UserResponse queryUser(String username, String systemCode, boolean refresh) {
```

不要机械写成：

```java
public UserResponse queryUser(
        String username,
        String systemCode,
        boolean refresh
) {
```

只有一行确实过长、阅读困难时才换行。

---

# 18. 注释规范

使用中文注释。

方法 Javadoc 保持紧凑。

推荐：

```java
/**
 * 根据用户名查询用户。
 * @param username 用户名
 * @return 用户信息
 * @throws UserNotFoundException 用户不存在
 */
```

不要：

```java
/**
 * 根据用户名查询用户。
 *
 * @param username 用户名
 *
 * @return 用户信息
 *
 * @throws UserNotFoundException 用户不存在
 */
```

不要写代码已经能表达的废话注释。

错误：

```java
// 创建对象
UserResponse response = new UserResponse();

// 设置用户名
response.setUsername(username);

// 返回结果
return response;
```

有价值的注释主要解释：

- 为什么这样做。
- 特殊业务规则。
- 非常规协议行为。
- 为什么不能使用通常实现。
- 容易被后续开发误改的地方。

例如：

```java
// Wizard 登录失效时可能返回 HTTP 200，但 data=false，不能仅通过 HTTP 状态码判断登录状态。
if (Boolean.FALSE.equals(data)) {
    sessionService.invalidate(token);
}
```

---

# 19. 类格式

类最后一个字段、成员或方法与最终 `}` 之间保留一个空行。

正确：

```java
public class UserServiceImpl implements UserService {

    public UserResponse query(String username) {
        return null;
    }

}
```

# 20. 配置规范

配置文件强调：

> **显式、直接、可读。**

配置化不等于环境变量化。

推荐：

```yaml
runtime:
  script-path: runtime/video.js
```

不要默认写：

```yaml
runtime:
  script-path: ${RUNTIME_SCRIPT_PATH:runtime/video.js}
```

同样推荐：

```yaml
sync:
  interval: 30m

remote:
  base-url: http://127.0.0.1:8080
```

不要机械改成：

```yaml
sync:
  interval: ${SYNC_INTERVAL:30m}

remote:
  base-url: ${REMOTE_BASE_URL:http://127.0.0.1:8080}
```

只有项目明确需要环境变量覆盖时，才使用 `${...}`。

原则：

> Java 代码可以通过工具减少样板，配置文件应尽量直接看到真实值。

# 21. Spring 配置

禁止通过配置掩盖代码设计问题。

不要：

```properties
spring.main.allow-bean-definition-overriding=true
spring.main.allow-circular-references=true
```

如果出现：

```text
Bean 重名
循环依赖
```

从代码结构解决。

不要为了“先启动起来”打开这些开关。

---

# 22. `@Bean` 生命周期

避免字符串形式：

```java
@Bean(destroyMethod = "shutdown")
```

优先使用：

- `AutoCloseable`。
- Spring 生命周期接口。
- 类型自身支持的资源管理。
- 明确的生命周期 Bean。

避免依赖字符串方法名。


```text

MyBatis-Plus
```

```text
Flyway
```

```text
Mapper

数据库配置
Redis
Migration
```

# 24. 参数校验

简单请求校验可以使用：

```java
@NotBlank
@NotNull
@Valid
```

例如：

```java
@Data
@FieldDefaults(level = AccessLevel.PRIVATE)
public class CreateStoryRequest {

    @NotBlank
    String name;

    @NotNull
    LocalDate releaseDate;

}
```

复杂业务规则放 Service。

例如：

```text
上线时间必须晚于评审时间
只有评审通过才能认领
上一阶段完成才能进入下一阶段
```

这些属于业务规则，不要全部做成复杂自定义 Validation 注解。

# 25. 外部系统实现原则

存在以下资料时：

- HAR。
- 抓包。
- 真实 HTTP 请求。
- 真实 HTTP 响应。
- 真实 JSON。
- 原系统代码。
- 用户提供的接口样例。

必须优先依据事实实现。

优先级：

```text
真实行为 / 抓包 / 原代码
        ↓
用户提供的原始材料
        ↓
官方或项目文档
        ↓
合理推测
```

不得凭经验猜：

- URL。
- 参数。
- JSON 类型。
- Header。
- Cookie。
- 登录步骤。
- 状态码。
- 成功条件。
- 分页方式。
- 字段含义。

如果 HAR 和通常认知冲突，以真实 HAR 为准。

---

# 26. 不擅自优化第三方协议

假设真实返回：

```json
{
  "userName": "cfm",
  "status": "ACTIVE",
  "planId": "1001"
}
```

远端协议对象应该忠实表达：

```java
String userName;
String status;
String planId;
```

不要为了本地统一擅自改成：

```java
String username;
UserState state;
String iterationId;
```

可以在 Service 中转换成本地对象。

原则：

> Remote Model 服从远端协议，Domain Model 服从本地业务。

---

# 27. 异常处理

禁止吞异常。

错误：

```java
try {
    doSomething();
} catch (Exception exception) {
    log.error("error");
}
```

然后继续返回成功。

正确：

```java
try {
    doSomething();
} catch (RemoteException exception) {
    log.error("调用 Wizard 失败，featureId={}", featureId, exception);
    throw new BusinessException(ErrorCode.WIZARD_CALL_FAILED, "调用 Wizard 失败");
}
```

异常只有两种合理处理：

1. 真正处理并恢复。
2. 向上传递明确失败。

不要悄悄忽略。

---

# 28. 全局异常

Controller 不要重复写大量 try/catch。

优先统一使用：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
}
```

业务异常、参数异常、远端调用异常等统一转换响应。

---

# 29. 日志规范

日志必须有实际诊断价值。

应该能够回答：

- 发生了什么。
- 哪个业务对象。
- 哪个外部系统。
- 当前结果是什么。
- 失败在哪一步。

推荐：

```java
log.info("Wizard 登录成功，username={}", username);
```

```java
log.warn("Wizard 会话失效，username={}", username);
```

```java
log.error("同步 Feature 失败，featureId={}", featureId, exception);
```

不要：

```java
log.info("进入方法");
log.info("开始执行");
log.info("执行完成");
```

除非这些日志确实用于必要的生命周期诊断。

---

# 30. 可靠性设计

对于：

- MQ。
- 消息通知。
- 系统同步。
- 外部接口提交。
- 可补偿任务。

如果项目确实需要可靠性机制，通常优先：

```text
正常实时路径
    +
持久化真实状态
    +
失败后台补偿
```

例如：

```text
业务事务
    ↓
Outbox
    ↓
实时异步发送
    ↓
失败
    ↓
定时扫描补偿
```

数据库扫描通常作为兜底，而不是唯一实时路径。

只有项目确实需要时才实现，不要默认所有功能都套 Outbox。

---

# 31. 抽象与扩展

只有真实存在多个实现时，再设计统一抽象。

例如真实存在：

```text
RocketMQ
HTTP
其他通知方式
```

可以设计：

```java
public interface NotificationProvider {

    void send(NotificationMessage message);

}
```

实现：

```text
RocketMqNotificationProvider
HttpNotificationProvider
```

但不要为了“以后可能扩展”默认给所有逻辑套：

```text
Strategy
Factory
Provider
Adapter
Executor
Context
Template
```

原则：

> 有真实变化点再抽象，不为想象中的变化点设计框架。

---

# 32. 控制需求范围

严格按照当前需求实现。

如果当前只要求：

```text
先实现一个列表接口验证登录链路
```

就只围绕该需求实现必要内容。

不要顺手增加：

- 详情。
- 新增。
- 修改。
- 删除。
- RBAC。
- Redis。
- MQ。
- 缓存。
- Swagger。
- Docker。
- Kubernetes。
- 审计。
- 导入导出。
- 未来扩展框架。

原则：

> 当前需求做完整，比提前做未来需求重要。

---

# 33. 最小修改原则

修改已有工程时，只修改完成当前需求所需要的文件和代码。

默认不要：

- 顺手格式化整个工程。
- 批量修改无关代码。
- 批量改名。
- 移动无关文件。
- 重构无关模块。
- 顺手统一全部代码风格。
- 顺手替换已有技术实现。
- 顺手清理与当前问题无关的“历史问题”。

即使发现无关问题，也不要自动扩大修改范围。

可以说明问题，但不要未经要求直接处理。

原则：

> 当前任务改当前任务，不借机改整个工程。

---

# 34. 不擅自修改已确认设计

禁止：

用户已经确认单 Maven 模块，Agent 自行改成 Maven 多模块。

用户已经确认字段属于 Story，Agent 自行拆成关联表。

用户已经确认某变化不触发拆分，Agent 自行修改拆分规则。

用户已经确认当前不使用数据库，Agent 提前增加数据库层。

用户已经确认接口来自 HAR，Agent 根据经验自行重写协议。

发现已有设计存在可改进之处，可以指出，但未经要求不要直接修改。

# 35. 已确认问题不重复讨论

已经记录在以下位置的明确结论：

```text
AGENTS.md
docs/decisions.md
README.md
设计文档
交接文档
```

默认视为已经确认。

后续 Agent 不要：

- 重复提出相同架构方案。
- 重复要求用户确认同一问题。
- 因为新会话重新推翻已有结论。
- 忽略已有设计记录重新从零分析。

只有出现以下情况才重新讨论：

- 用户明确要求修改。
- 新事实与旧决策发生冲突。
- 原决策已经无法满足当前需求。

# 36. 依赖复用优先

新增功能前，优先检查当前工程已经存在的：

- Maven 依赖。
- 工具类。
- Client。
- Service。
- 公共组件。
- 配置。
- JS / CSS 前端库。

已有能力能够满足时，不要增加功能重复的新依赖。

例如：

项目已经有可用 HTTP Client，不要仅为了一个新接口再增加另一套 HTTP Client。

项目已有工具类可以完成字符串处理，不要为了一个简单操作增加新的大型工具包。

原则：

> 先复用，再新增。

# 37. 数据模型尊重真实业务

数据结构应表达真实业务事实。

例如：

```text
同一个真实 Story

上线批次 B：10 月 20 日
```

如果业务上属于两个执行单元，就创建两个执行单元。

不要为了减少数据量，只在原对象上不断覆盖：

```java
story.setReleaseTime(...);
```

原则：

> 数据模型首先反映事实，再考虑展示方便。

# 38. 时间模型

如果一个阶段真实存在多个时间区间：

```text
09:00 - 10:00
14:00 - 16:00
```

真实占用是：

```text
3 小时
```

不是：

```text
09:00 - 16:00 = 7 小时
```

因此需要时保存多个时间区间，并分别计算：

```text
整体跨度
实际占用
```

不要为了 UI 展示简单而破坏原始时间事实。

# 59. 事实、决策、实现分离

项目中统一按照：

```text
reference/         原始事实
docs/decisions.md  已确认决策
src/               当前实现
```

理解项目。

三者不能混为一谈。

例如：

```text
reference/har/login.har
```

表示真实系统实际如何请求。

```text

```

表示最终决定如何在本项目中实现。

```text

```

表示当前实现结果。

如果三者冲突：

```text
新事实
    ↓
重新判断决策
    ↓
修改实现
```

不要因为现有代码已经这么写，就反推真实系统一定如此。

# 64. AI / Codex 行为规范

Codex 修改代码时：

1. 先理解，再修改。
2. 先阅读适用的 `AGENTS.md`。
3. 先检查 `reference/README.md` 和相关参考资料。
4. 先检查 `docs/decisions.md`。
5. 优先修改必要文件。
6. 不扩大任务范围。
7. 不为了展示能力进行大规模重构。
8. 不自行添加用户没有要求的基础设施。
9. 不自行修改已经确认的业务规则。
10. 不猜测已有外部系统接口。
11. 不把理论最佳实践凌驾于当前项目真实需求之上。
12. 能复用现有代码就复用。
13. 能复用现有依赖就不增加重复依赖。
14. 默认不主动编写单元测试、集成测试或测试用例。
15. 默认不主动执行编译、启动、接口调用或其他验证操作。
16. 只有用户明确要求测试、编译、运行或验证时才执行。
17. 未实际执行过的操作，不得描述为“已通过”或“已验证”。
18. 不因为任务简单而擅自扩大到重构、测试、监控、部署等其他范围。
19. 新工程没有特别说明时使用 `com.paic.stock`。
20. 新工程前端没有特别说明时使用 Vue 3 静态页面。
21. Vue 3 默认直接放入 Spring Boot `static`。
22. 前端 JS / CSS / Vue 默认使用本地文件，不使用 CDN。
23. 默认不创建独立 Node / Vue 工程。
24. 用户主动提供的重要材料默认保存到 `reference/`。
25. 已确认的重要决策记录到 `docs/decisions.md`。
26. 不重复要求用户提供已经保存过的材料。
27. 不重复讨论已经确认且没有新冲突的设计。

# 66. 推荐 Spring Service 示例

```java
@Service
@RequiredArgsConstructor
@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)
public class UserServiceImpl implements UserService {

    WizardClient wizardClient;

    /**
     * 查询用户。
     * @param username 用户名
     * @return 用户信息
     */
    @Override
    public UserResponse query(String username) {
        WizardUser wizardUser = wizardClient.queryUser(username);

        UserResponse response = new UserResponse();
        response.setId(wizardUser.getId());
        response.setUsername(wizardUser.getUsername());
        response.setState(convertState(wizardUser.getStatus()));

        return response;
    }

    /**
     * 转换用户状态。
     * @param status Wizard 用户状态
     * @return 本地用户状态
     */
    private UserState convertState(String status) {
        if ("ACTIVE".equals(status)) {
            return UserState.ENABLED;
        }

        return UserState.DISABLED;
    }

}
```

# 73. 最终代码自检

完成代码修改时，重点检查代码本身。

## 结构

- 是否无意义增加了包？
- 是否无意义增加了类？
- ServiceImpl 是否放在 `service.impl`？
- 是否出现重复 DTO / VO / BO？
- 是否擅自拆成 Maven 多模块？
- 是否无关修改了其他模块？

## Java

- 是否出现 `var`？
- 是否存在不必要 Stream / Lambda？
- 是否可以使用 Lombok 减少样板？
- Spring Bean 是否符合 `@RequiredArgsConstructor + @FieldDefaults` 风格？
- 枚举是否使用同行行尾注释？

## 业务

- 是否严格遵循已确认规则？
- 是否实现了用户没要求的内容？
- 是否为了简化代码破坏真实业务关系？
- 是否忽略了 `docs/decisions.md` 中已经确认的结论？

## 外部系统

- 接口是否依据真实资料？
- 是否检查了 `reference/`？
- 是否猜测 URL / JSON / Cookie / Header？
- 是否擅自修改远端字段语义？

## 配置

- 是否无意义使用 `${ENV:default}`？
- 固定值是否可以直接写？

## 前端

- 是否无意义创建独立 Vue 工程？
- 是否无意义加入 npm / Vite / Webpack？
- JS / CSS 是否可以直接使用本地静态资源？
- 是否无意义使用 CDN？
- 是否无意义加入 Axios？

## 参考材料

- 用户新上传材料是否已保存？
- 原始文件是否保持不变？
- 同名文件是否错误覆盖？
- `reference/README.md` 是否需要更新？

## 决策

- 是否产生了新的重要设计决策？
- `docs/decisions.md` 是否需要更新？
- 是否存在新旧决策冲突？

## 异常与日志

- 是否吞异常？
- 日志是否有实际业务上下文？

默认不增加测试与验证步骤。

# 74. 最核心的编码与协作哲学

最终统一为：

> **配置显式，代码简洁。**

> **样板代码可以隐藏，业务语义不能隐藏。**

> **真实业务优先于技术形式。**

> **可读性优先于代码行数。**

> **简单结构优先于过度抽象。**

> **真实协议优先于主观猜测。**

> **当前需求优先于假想未来。**

> **先复用已有能力，再增加新依赖。**

> **修改已有工程遵循最小修改原则。**

> **失败要明确，不要悄悄吞掉。**

> **测试和验证按需执行，不默认增加。**

> **前端能静态解决，就不要默认引入前端工程化体系。**

> **用户提供的原始材料属于项目资产，不属于一次性会话内容。**

> **原始事实放 reference，已确认决策放 docs/decisions.md，代码实现放 src。**

> **已经确认的问题，没有新事实冲突时不要反复讨论。**

> **已经确认的设计，未经明确要求不要擅自修改。**

最终目标不是生成“理论上最优雅”的代码，而是生成：

> **符合当前项目实际情况、符合个人代码习惯、结构简单、代码简洁、事实可追溯、决策可延续、容易阅读、容易维护，并方便后续继续开发和交接的工程。**
